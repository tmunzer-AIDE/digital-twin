# Full stack twin coverage audit

Reviewed on October 1, 2026. The semantic-model architecture is still the right direction, but **changed-field allowlists and passing detectors cannot certify a full stack simulation**. The main missing safeguard is a proof that every mechanism relevant to a property was represented, including unchanged configuration, generated configuration, external inputs, and deployment state.

The [October 5 attribute and identification review](mist-attribute-review.md) adds a current per-occurrence disposition ledger, closes further selector/path/client-identity gaps, and expands the narrowly reviewed cosmetic allowlist. Counts and classifications below describe the original October 1 inventory state.

This review found reproducible bypasses, corrected several in the existing engine, inventoried the available specification, and tightened the proposed architecture. It did not implement or validate a production OSPF, BGP, EVPN, firewall, SSR, or onboarding simulator. No live Mist API requests or configuration changes were made.

## Remaining architectural blind spots

**Unchanged features and activation.** A modeled edit can activate an unsupported existing feature: enabling a protocol, assigning a profile, resolving a variable, changing a rule's scope, or changing a fabric role. Compare complete effective baseline/proposed configurations and retain unsupported constructs as opaque semantic boundaries. Require coverage for all relevant reads, not just edited leaves. The current gates catch some specific activation cases; there is no general feature-completeness proof.

**Population and intent.** The existing engine still permits a zero-observed-client WLAN disable to return `SAFE`. An absence of current observations does not prove an empty population or an approved decommission. Evaluate configured potential cohorts, disconnected clients, new joins, and required services. Baseline preservation is useful but can preserve a pre-existing isolation defect. Desired connectivity/isolation and intentional removals need explicit property scope. Report which cohorts and obligations were evaluated.

**Source scope and identity.** VLAN IDs, prefixes, route-policy names, and labels are not globally unique. Model bridge domains, fabrics, VRFs, tenants, devices, and sites explicitly. Join contexts only through actual links, tunnel mappings, leaks, or fabric membership. A site identifier alone is insufficient when several VRFs reuse a prefix. Conversely, an EVPN bridge domain can intentionally span sites. Preserve structural path tokens instead of flattening literal IP/name keys into ambiguous dotted paths.

**Compilation and defaults.** Root replacement, dash deletion markers, explicit null, omission, empty objects, list ordering, union selection, inheritance, overrides, and defaults need contracts per endpoint and platform. The current null/absent canonicalization is a compatibility convention; it must not become a universal mutation rule. Global metadata exclusions likewise cannot be reused across resource contexts. New enum values, opaque additional CLI, undocumented defaults, and read-only field assumptions need explicit coverage outcomes.

The pinned September `switch_bgp_config_neighbor` still does not expose `disabled`, while the committed extract adds it through a local patch. The gateway neighbor schema does expose it. This discrepancy needs explicit version/platform validation and tracked override evidence; a field's presence on a sibling platform does not certify switch support.

**Discovery and drift.** A snapshot must prove collection completeness: pagination, privileges, errors, acquisition window, timestamps, optional-domain discovery, and device/cloud version. A missing or forbidden response cannot mean an empty domain. Generated commands and derived settings are configuration oracles, not proof of applied state. A healthy baseline BGP session or tunnel does not establish a healthy proposed route or session. Expire observations according to causal dependencies, not only wall-clock age.

**Deployment and retained state.** A final-state batch can work while mixed deployment states fail. Independent Mist activation, config-push schedules, device reboot, NAC reauthentication/CoA, existing DHCP leases, NAT entries, and SSR sessions matter. Explore activation dependencies, failure/rollback states, and old/new session cohorts. An unexplored timing class or exhausted budget blocks the corresponding assurance.

**Uncertainty and selection.** Keep justified behavior separate from possible behavior caused by missing knowledge. A possible bad path is an unresolved risk unless its feasibility is proved. A definite violation survives unrelated uncertainty. A possible good ECMP/path branch cannot prove universal delivery. Unknown earlier firewall/NAC/routing terms cannot simply be skipped. Related unknown facts must share identities; treating repeated reads as independent can invent impossible paths.

**Incremental evaluation.** Use the union of baseline and proposed dependency closures, including removed references, negative predicates, default routes, shared services, templates, site groups, label variables, fabric generation and observation dependencies. Renaming or reassigning an object can alter the graph even if its payload looks cosmetic. Incremental results must equal a full recomputation; if the closure is unknown, broaden evaluation and retain the missing-data gap.

**Redaction and fidelity.** Existing IP pseudonymization preserves equality but not subnet membership; name hashing does not preserve substring matching. Broad credential stripping can also remove certificate metadata and routing-community information. Do not claim that redacted captures reproduce routing or matching semantics unless those relationships are preserved and verified. Keep confidential material out of exports; use explicit unknown credential facts or a non-exported comparison result. Never equate two stripped values as proof that authentication keys match.

## Routing and fabric validation obligations

The current OSPF check detects participation/metric/prefix changes and some observational peer breaks. The BGP check detects selected peering changes. Neither computes an organization RIB/FIB, route-policy fixed point, or end-to-end forwarding. EVPN is not implemented. ## Required coverage contract

The new compiler must emit a **coverage receipt** with each model fragment: source operation/schema and structural path, resource context, effective inputs/defaults, model/platform/firmware versions, supported value grammar, dependencies, observation validity, and referenced validation evidence. Preserve unconsumed features as explicit opaque fragments.

An affected property can be satisfied only when its relevant baseline/proposed fragments, generated configuration, scenario classes and input facts are covered. An unsupported feature can be excluded only with a documented non-interference proof for that property in every evaluated stage. For example, a disabled protocol may be irrelevant only if the batch and rollout cannot activate it. An allowlisted leaf, no IR delta, a passing check, or a cloud-accepted payload is insufficient.

Feature registration is contextual and defaults to unsupported. A new field, enum, union branch, platform/version, opaque CLI command, or operational action must require a coverage disposition. An action contract must account for side effects; do not infer inertness from an unchanged JSON object. Positive results must identify the property/cohort/stage and the bounds of the model. Keep proven violations and unresolved obligations together.

This contract is now a requirement in the [revised architecture](full-stack-twin-design.md#coverage-and-unknown-inputs). It remains implementation work; the current production engine does not enforce a general receipt-based completeness gate.

## Validation workflow and release gates

For **each field/action context**, generate add/change/remove, default/explicit-default, null/omission/empty, valid type/enum boundaries, wrong types, map/list/union and reorder cases where meaningful. Repeat at supported org/template/site/profile/device origins and through variable resolution. Include an unsupported feature already present in the baseline that becomes relevant through another change. Schema-shape tests are generated from the inventory; human-reviewed semantic expectations come from the mechanism contract.

For **each mechanism**, require a known working and known failing case, exact counterexample paths, uncertainty cases, default behavior, supported platform/version cases, and independent baseline calibration. Hypothetical vendor outcomes need separately authorized controlled experiments; until then record the feature as uncalibrated or conditional. Mist-derived settings, generated commands, stats and events validate the baseline only. Do not count the same parser's output as its own independent oracle.

For **composition**, require NAC + WLAN + wired compensating migrations; site-variable NAC labels with different site values; routing policy + BGP + EVPN + WAN propagation; firewall/NAT plus route changes in both directions; fabric/AP trunk + Mist Edge tunnel loops; new joins versus retained sessions; and complete, partial, failed and rollback rollout states. Cover harmless individual edits that fail only together, as well as individually breaking edits that work together.

For **the solver and cache**, use a small independent exhaustive oracle on bounded topologies, generated packet classes and truth tables. Check that symbolic results match concrete enumeration, incremental matches full recomputation, adding uncertainty cannot manufacture satisfaction, duplicate/order-independent final overlays behave consistently where promised, and budget/cancellation/restart failures are explicit. Metamorphic laws need preconditions: adding a deny rule is not monotone when it includes nonterminal actions, and changing route advertisements is not generally monotone under policy selection.

Release readiness is evidence per mechanism/context, not a test-count target or “100% OAS covered.” CI must fail if a new inventory entry has no explicit disposition, a required semantic case is missing/skipped, or a positive result has no complete receipt. Unsupported dispositions may be accepted for a bounded release, but must produce unresolved obligations when relevant. Keep live calibration separately identified and never silently treat unavailable credentials as a passing live test.
